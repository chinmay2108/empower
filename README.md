# Empower

Empower helps people who are new to a city keep showing up to the same few groups until they have friends there. It is a follow-through app, not an event search: it helps you commit, go, check in, and go back.

Course project for Coding with GPT (Darden 8633, AY'27). Team: Chinmaya, Daniel, Saumya.

## Run it

**Easiest:** open `index.html` in Chrome. No install needed.

**Like a real website (recommended before testing a PR):**

```
cd empower
python3 -m http.server 8000
```

Then open http://localhost:8000.

**Live site:** GitHub Pages, at https://chinmay2108.github.io/empower/ once Pages is turned on (Settings > Pages > Deploy from branch > `main`).

**Install it like an app:** open the live site on your phone. iPhone (Safari): Share > Add to Home Screen. Android (Chrome): menu > Install app. It opens full-screen, works offline, and picks up new versions the first time it's opened after a deploy (no reinstall). This only works on the live site (https), not when you open `index.html` as a file; the app itself works the same either way. How it works: `manifest.webmanifest` (name, icons) and `sw.js` (saves every file for offline). Adding a page or script? Add it to the list in `sw.js`; `tests/pwa.test.js` checks.

**Clickable mockups of every flow:** open `prototype/index.html` (live: https://chinmay2108.github.io/empower/prototype/). Sample data, no logic. Use them to agree on a screen before building it.

**Start from a clean slate:** open the browser console (Cmd+Option+J) and run `Empower.store.resetAll()`, then reload.

## Stack

HTML, CSS, and plain JavaScript, as the course requires (no frameworks). Data is saved in the browser's localStorage for now. A Python backend comes later, when features need shared data between users (matching, chat).

## How the code is organized

| Layer | Where | Job |
| --- | --- | --- |
| View | `index.html`, `pages/*.html` | Structure only. No colors or logic. |
| Look | `css/styles.css` | One shared stylesheet. Colors, type, spacing and radius live in variables at the top. Change them once and every page follows. |
| Controller | `js/home.js`, `js/onboarding.js`, `js/events.js`, `js/group.js`, `js/commit.js`, `js/prep.js`, `js/reflect.js`, `js/me.js` | One file per page. Reads and writes data through the store, applies the feature's rules, updates the page. |
| Model | `js/store.js` | The only file that touches saved data. |
| Rules | `js/logic.js`, `js/schedule.js` | Pure functions (same input, same output): picks, conflicts, check-in windows, show-up score, progress, sessions. Unit tested in `tests/`. |
| Shared UI | `js/ui.js` | Bottom nav, date formatting, `Empower.log` for observability. |
| Seed data | `data/groups.js`, `data/population.js` | 15 sample recurring groups and 500 **synthetic** people (generated by `scripts/generate_population.py`). Invented, not real listings or users. |

Dependencies point one way: pages depend on the store and the shared helpers, never the other way around.

Every page loads scripts in this order: `data/groups.js`, `js/ui.js`, `js/store.js`, `js/schedule.js`, `js/logic.js`, then its own file. The full list of functions screens can call is in [docs/mechanics.md](docs/mechanics.md).

**Tests:** `node --test tests/*.test.js` (GitHub runs them on every PR).

**Demo:** Me > Demo tools moves the app clock so you can check in to a session without waiting for it.

## Data model

| Entity | Key fields | Created by |
| --- | --- | --- |
| Profile | name, interests[], freeSlots[], step, traits | Onboarding |
| Answer | questionId, choice, at | Onboarding quiz and daily question |
| Group | id, name, category, interests[], weekday, time, durationMin, venue, structure | Seed data |
| Session | id (`groupId@YYYY-MM-DD`), groupId, startsAt, endsAt | Generated by `schedule.js` |
| Commitment | id, sessionId, groupId, startsAt, leaveAt, travelMode, status | This week page |
| Reflection | id, commitmentId, enjoyed (1-3), talkedToSomeone, wouldReturn, note | Check-in page |

| Person | id, name, interests[], freeSlots[], step, warmth, reliability, memberships[] | Synthetic population (read-only) |
| Connection | personId, sessionId, groupId | Added after a session |
| Message | personId, from, text, sessionId? | Chat |

A Group has many Sessions. A Commitment points to one Session. A Reflection points to one Commitment. A Connection points to one Person; it's a match when that person adds back (decided by `js/people.js`).

## Observability

Use `Empower.log("area.what_happened", { details })` for key moments. Logs show in the browser console as `[empower] ...`. In Session 11 we will forward these to PostHog from that one function.
